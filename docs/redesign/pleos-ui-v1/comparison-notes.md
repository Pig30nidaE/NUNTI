# 실제 앱과 Figma UI 비교

Figma에서 내보낸 주야간 8개 PNG와 기존 앱의 실제 기준 화면을 직접 확인했다. [Before/After 4행 보드](comparison/before-after-day.png)와 [주야간 제안 비교](comparison/day-night-proposals.png)를 생성했다. 보드에서는 각 화면을 50%로 축소하며, [정규화 원본](comparison/normalized/)은 1682×1210으로 보존한다.

Before는 기존 설치 APK의 실제 production 경로다. After는 승인 A 원화를 사용하는 Figma UI 제안이며 새 Android UI의 구현 결과가 아니다. 기존에 저장된 캐릭터·목적지·점수와 디자인 예시의 값은 서로 다르다. 따라서 동일 데이터의 픽셀 일치 검증으로 해석하지 않는다.

전체 화면 2560×1440에서 앱 영역 `[853,90]–[2535,1300]`만 잘라 1682×1210으로 맞춘다. Figma도 같은 크기의 앱 프레임을 사용한다. 차량 정보, 상태바와 하단 내비게이션·공조 영역은 비교 대상 밖이며 앱 소유 UI로 다시 만들지 않는다.

## 출발 전

| 차이 | 실제 앱 | Figma 제안 |
|---|---|---|
| 첫 화면의 중심 | 내비 연동·API 시험·파일 입력·이미지 생성 방식이 함께 보이고 경로 이미지가 아래로 이어진다. | 기본 눈티와 경로를 왼쪽에, 이번 여정 입력을 오른쪽에 묶는다. |
| 경로 확인 | 여러 내비 및 경로 도구 사이에 경로 확인이 분산된다. | 목적지 불러오기·내비 열기·경로 확인을 같은 카드에 모으고 다른 입력 방법을 별도 동작으로 묶는다. |
| 선택한 기분 | 현재 기본 생성 방식 화면에는 목적지·그곳의 느낌·방문 이유가 보인다. A 모드의 명시적 기분은 별도 선택 영역이다. | 목적지 유형·도로 유형과 직접 고르는 세 가지 기분을 첫 화면에 표시한다. 차량 신호에서 감정을 추론하는 표현으로 바꾸지 않는다. |
| 주요 동작 | 생성 버튼이 오른쪽 입력 카드의 하단에 있으며 지도와 추가 도구는 첫 화면 아래로 이어진다. | 자동 저장 설명과 생성 버튼을 카드 밖의 하단 행에 배치한다. |

## 정차 중 결과와 변형

| 차이 | 실제 앱 | Figma 제안 |
|---|---|---|
| 캐릭터 | 보관된 몽글콩 결과를 그대로 표시한다. | 승인 A의 바다·호기심 외형을 대표 이미지로 사용한다. 기존 저장 이미지를 교체했다는 뜻은 아니다. |
| 외형 설명 | 캐릭터 성격, 방문 이유, 옷차림·기념품·탄생 순간 등 기존 생성 모드 설명이 길게 이어진다. | 길의 패턴·목적지 장식·직접 고른 기분을 세 행으로 설명한다. |
| 모션 제어 | production A 결과는 정적 표시이고, 새 4초 모션은 별도 debug Activity다. | 다시 보기·움직임 줄이기·바로 보기를 같은 화면에서 제공하는 통합안을 표현한다. 실제 Studio 연결은 미구현이다. |
| 출발 동작 | 음성과 여정 선택 영역 아래에 출발 버튼이 있다. | 출발 버튼을 하단 주요 동작으로 두고 `목소리 듣기`, `여정 옵션 · 이야기`를 보조 영역으로 분리한다. |

## 주행 제한

| 차이 | 실제 앱 | Figma 제안 |
|---|---|---|
| 실제 노출 | D/30에서 시스템의 `주행 중에는 사용할 수 없습니다` 차단 화면이 보인다. | 정적 동반자 제안이다. 이 장치에서 런타임 노출이 승인됐다고 볼 수 없다. |
| 캐릭터 가시성 | Journey의 접근성 노드는 남지만 캐릭터는 시스템 오버레이 뒤에 가려진다. | 얼굴과 몸체가 큰 정적 이미지로 보이는 상태를 설계한다. 플랫폼이 허용할 때만 적용 가능한 화면이다. |
| 정보량 | 서비스 JSON은 ACTIVE/LIVE, D/30, canFinish=false를 기록한다. 보이는 화면에는 점수나 피드백이 없다. | 평가 대기·주행 시간·실시간 신호 출처만 간단하게 보여준다. 상세는 정차 후로 미룬다. |
| 조작 | 실제 가시 화면에서 Nunti 버튼을 사용할 수 있다고 검증되지 않았다. | 음성 끄기와 외부 내비 열기만 제안하며, 이 동작들의 주행 허용성도 별도 확인 대상이다. |

차단 화면을 없애거나 제한 정책을 바꾸어 비교를 만들지 않는다. 보드의 Before에는 `ACTUAL PLATFORM BLOCK`, After에는 `Driving visibility is NOT runtime-approved` 라벨을 붙인다.

## 도착 후

| 차이 | 실제 앱 | Figma 제안 |
|---|---|---|
| 읽기 크기 | 넓은 창에 작은 제목·점수·상세 텍스트가 좁은 세로열로 놓인다. | 눈티, 요약 지표, 평가 설명, 세부 기록을 카드로 구분하고 글자 크기를 높인다. |
| 요약 지표 | 점수와 주행 시간이 서로 떨어져 있다. | 점수와 함께한 시간을 나란한 두 카드로 묶는다. |
| 신호 부족 | 항목마다 `평가 불가`와 `수신 없음`이 반복된다. | 신호 부족 설명과 평가 가능한 범위를 먼저 보여주고 미수신 항목은 점수에서 제외한다고 안내한다. 예시의 `평가 대기/0%`는 실제 56점 리포트와 다른 샘플 데이터다. |
| 상세와 복귀 | 모든 항목과 이벤트가 한 화면에 이어지고 돌아가기·내비 열기가 오른쪽 아래에 작게 놓인다. | 세부 기록 진입과 눈티로 돌아가기를 구분한다. 새 기록 목록이나 공유 기능의 구현을 뜻하지 않는다. |

## 주야간과 검증 경계

Day/Night 보드는 Figma 제안끼리 비교한다. 기존 production 화면은 고정 밝은 색이며 이번 baseline에 대응되는 production 야간 캡처는 없다. Figma의 어두운 테마가 실제 앱에서 작동한다고 주장하지 않는다.

원본 크기에서 네 상태의 제목, 캐릭터, 입력값, 주요 버튼이 프레임 안에 표시되는 것을 확인했다. 야간의 quiet 버튼 문구도 밝게 표시된다. 주요 텍스트의 겹침이나 잘림은 발견하지 않았다. 토큰의 수치 대비 검증은 [별도 결과](token-contrast.json)에 있으며, 이 이미지 검토가 접근성·주행 적합성 인증을 대신하지 않는다.

시각 마감 검토에서 Secondary 버튼의 직선 외곽선과 도착 후 세부 기록 카드의 버튼 하단 여백을 발견했다. 디자인 담당자는 외곽선의 `OUTSIDE` stroke가 clipping으로 잘리는 원인을 확인해 `INSIDE`로 바꿨다. 리포트 카드 높이도 재배분하고 중복 설명을 정리했다. 최종 주야간 이미지에서 외곽선이 연속으로 표시되고, 세부 기록 버튼 아래 여백이 확보된 것을 다시 확인했다. 결과 화면의 보조 버튼도 `여정 옵션 · 이야기`로 갱신됐다. 비교 보드는 이 수정본으로 재생성했다.

재현 명령은 `.worktrees/server/backend/.venv/bin/python scripts/build_nunti_ui_comparison.py`다. 원본 export가 모두 있어야 보드를 만들며, 입력 파일을 수정하지 않는다. [manifest](comparison/manifest.json)에는 입력 12장의 SHA-256, 전체 크기, 크롭 좌표, 정규화 크기, 실제/제안 구분, Figma node ID·URL, 렌더링 라이브러리와 폰트 해시를 기록했다. [Figma 출처](exports/frame-sources.json)는 파일 키 `LHLHBra8ON3OdVW0qhBnbm`, 페이지 `15:4`의 네 상태 × 주야간 8개 프레임이다.

[결과 검증](comparison/verification.json)에서 Before 4장의 크롭 픽셀과 Figma 8장의 정규화 픽셀이 각각 원본과 동일함을 확인했다. 같은 입력으로 한 번 더 실행해 출력 이미지 14장과 manifest의 해시가 모두 동일한 것도 확인했다. 이는 비교 파일의 보존·재현성 검사이며 Before/After 디자인이 서로 동일하다는 뜻이 아니다.

실제 제한 상태와 복원 내역은 [runtime-verification.md](runtime-verification.md)에 있다. 새 UI의 Android 적용, 주행 노출 자격, 터치·TalkBack·큰 글씨·야간 런타임 검증은 이 비교 이후의 작업이다.
